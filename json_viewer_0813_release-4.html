json_mult_review.html — 뷰어 사양 문서

26_1st.json류 문제지 JSON을 렌더링하는 json_mult_review.html이 지원하는 문법을 정리한 문서. 새 문제/해설 텍스트를 JSON에 작성할 때 이 문서 기준으로 작성하면 뷰어에서 깨지지 않는다.

수식 구분자

  • 인라인 수식: \( ... \)
  • 디스플레이 수식: \[ ... \]
  • 그 밖의 일반 텍스트는 그대로 escape되어 출력됨 (HTML 태그 삽입 불가)

\text{...} 인자를 그대로 출력(평문) 위와 같은 이유로 JSON은 아직 \text{} 벗긴 평문 상태 유지

새 명령어를 추가하기 전에는 항상 실제 JSON 데이터에서 쓰인 전체 명령어 목록을 뽑아 대조한다:

import json, re
cmds = set()
for fn in ['26_1st.json', '26_2nd.json']:
    d = json.load(open(fn, encoding='utf-8'))
    for p in d['problems']:
        text = p.get('question','') + ' '.join(p.get('choices') or []) + ' '.join(p.get('solution') or [])
        cmds |= set(re.findall(r'\\[a-zA-Z]+', text))
print(sorted(cmds))

그리고 texToHtml을 Node로 분리해 모든 문항의 모든 텍스트 필드를 실제로 돌려보고 \[A-Za-z]+ 패턴이 출력에 남아있지 않은지(=처리 안 된 명령어가 없는지) 회귀 테스트할 것. 브라우저 없이도 <script> 내용만 추출해 module.exports로 Node에서 실행 가능하다.

처리 원칙

  • 화살표 등 새 기호가 필요하면 JSON이 아니라 뷰어(texToHtml)에서 추가한다. JSON은 표준 LaTeX 표기를 그대로 쓰는 "원문 데이터"로 유지하고, 화면에 어떻게 그릴지는 뷰어 책임으로 분리한다. JSON에서 유니코드 기호로 직접 바꿔치기하면 같은 명령어를 쓰는 다른 모든 문제를 하나씩 찾아 고쳐야 하고, 다음 시험지 JSON을 만들 때도 표준 표기를 못 쓰게 된다.
  • 새 명령어를 추가할 때는 기존 명령어(\times, \pm 등)와 같은 위치 (그리스 문자 처리 이후, ^/_ 처리 이전)에 넣는다.
  • 명령어 이름이 서로의 접두사인 경우 반드시 긴 것부터 먼저 검사해야 짧은 명령어가 긴 명령어를 가로채지 않는다. 실제로 겪은 충돌 사례:
  • \rightarrow/\to, \Rightarrow/\rightarrow
  • \leftarrow vs \left (leftarrow가 먼저 와야 함)
  • \rightarrow vs \right (rightarrow가 먼저 와야 함)
  • \pmod vs \pm (pmod가 먼저 와야 함)
  • \cdots vs \cdot (cdots가 먼저 와야 함)
  • \infty vs \in (infty가 먼저 와야 함) 새 명령어를 추가할 때마다 기존 목록 전체와 접두사 겹침이 없는지 확인.
  • \{, \} (이스케이프된 리터럴 중괄호)는 파서의 기본 중괄호 그룹핑 ({...} = 인자 묶음)과 반드시 구분해서 처리해야 한다. 구분 없이 두면 \in\{2,4,6,8\} 같은 집합 표기가 깨진다 — 이스케이프 브레이스 검사를 일반 백슬래시 처리보다 먼저 넣을 것.

solution 필드 구조

solution은 배열이지만, 단일 원소 배열로 작성한다. 그 원소 안에 다음 구조를 \n(줄바꿈)으로 이어붙인 하나의 문자열을 담는다:

"진단 문구(핵심 개념/스킬 한 줄)\n풀이 단계1\n풀이 단계2\n..."

예:

"solution": [
  "복소수의 상등 조건 활용하기\n\\(\\overline{5i}=-5i\\)이므로 \\((x-2)+(x-y)i=0-5i\\).\n실수부: \\(x-2=0 \\therefore x=2\\). 허수부: \\(x-y=-5 \\therefore y=7\\).\n\\(x+y=2+7=9\\)"
]
  • 첫 줄(진단 문구)은 이 문제가 확인하려는 핵심 개념/스킬을 한 문장으로 요약한 것 ("~하기", "~할 수 있는가?" 등). 실제 풀이 단계가 아니다.
  • 뷰어는 p.solution.join(' ')으로 explanation을 만드는데, 배열 원소가 하나뿐이면 join이 구분자를 넣지 않으므로 내부의 \n이 그대로 보존된다. .p-explanation에 white-space:pre-line이 이미 적용돼 있어 \n이 실제 줄바꿈으로 렌더링된다 — 뷰어 코드 수정 불필요.
  • 여러 단계를 배열 원소로 쪼개 넣는 예전 방식(["단계1","단계2",...])은 쓰지 않는다. 그렇게 하면 join(' ')이 각 단계 사이에 공백만 넣어 한 줄로 뭉개진다.

문제지 미리보기 화면 상단 "📷 이미지 도구" 패널과, 각 문제에 이미 붙은 이미지 위에 뜨는 버튼들로 이미지를 관리한다. problems[i].images는 data URL 문자열의 배열이며, 이 도구들은 전부 그 배열을 직접 수정한다.

  1. 선택지 원문자(①②③④⑤) 누락: 이 문서의 "참조 파일과의 차이" 절에 선택지는 원문자를 붙이기로 이미 명시돼 있었는데도, 실제 렌더링 코드 (render()의 메인 카드 렌더링, buildPrintProblemHTML() 둘 다)는 p.choices를 그냥 <div>${renderMathText(c)}</div>로만 찍고 있어서 원문자가 전혀 안 붙고 있었음 — 스펙 문서와 실제 코드가 어긋나 있었던 사례. CIRCLE = ['①','②','③','④','⑤','⑥','⑦','⑧'] 배열을 추가하고 두 렌더링 함수 모두 ${CIRCLE[ci] || (ci+1)+'.'} ${renderMathText(c)} 형태로 수정.
  2. 문제 번호·난이도 배지가 화면 폭에 따라 멀리 떨어져 보임: .problem 카드에 max-width 제한이 없어서, 아주 넓은 화면(태블릿 가로모드 등, ~2400px)에서는 카드가 화면 폭 전체로 늘어나고, .p-head의 justify-content:space-between 때문에 번호(134번)와 난이도 배지 (mid)가 화면 양 끝까지 벌어져 마치 배지가 사라진 것처럼 보였음. .problem{ max-width:760px; } 추가로 해결.

  3. 난이도 배지 표기가 실제 사이트와 불일치: 이 뷰어는 diff 값 (low/mid/midhigh/high/top)을 영어 그대로 배지에 찍고 있었는데, 실제 math_practices 사이트(player.html)는 DIFF_LABEL 매핑으로 한글 배지(하/중/중상/상/최상)를 보여주고 있어서 두 화면의 배지 표기가 서로 달랐음. player.html의 매핑을 그대로 가져와 const DIFF_LABEL = { low:'하', mid:'중', midhigh:'중상', high:'상', top:'최상' }; 을 추가하고, 두 렌더링 함수 모두 ${DIFF_LABEL[diff] || diff}로 통일.

  4. 줄바꿈이 문자 그대로 \n으로 노출됨 (뷰어 버그 아님, JSON 생성 실수): senmath32_06_q138~149.json의 0141번처럼 (1)...(2)... 형태로 줄을 나눠야 하는 문제에서, question 텍스트 중간에 진짜 개행 문자가 아니라 백슬래시+n 두 글자("\n")가 그대로 들어가 있어서 화면에 \n이 글자로 찍혔음. Python으로 JSON을 만들 때 "...\\n(1)..."처럼 이중 백슬래시로 써야 할 걸 실수로 그렇게 썼지만 실제로는 진짜 개행이 필요한 자리였음 (Python 문자열에서 \\n은 문자 그대로 \+n 두 글자, \n 한 번만 써야 실제 줄바꿈 한 글자가 됨). senmath32_04·05·06 세 파일 전부에 같은 실수가 있어서 일괄 치환(content.replace('\\n', '\n'))으로 전부 고침. .p-question에 white-space:pre-line이 이미 적용돼 있으므로 실제 개행 문자만 넣으면 뷰어 코드 수정 없이 줄바꿈이 된다 — 문제 텍스트에 줄바꿈이 필요하면 JSON 생성 스크립트에서 반드시 진짜 개행 문자를 넣을 것, 백슬래시-n 두 글자를 넣지 말 것.

두 버그 모두 좁은 화면(모바일 세로모드, ~390px)에서는 우연히 눈에 덜 띄거나 안 보였을 수 있어서, 새 기능을 검증할 때는 좁은 뷰포트뿐 아니라 아주 넓은 뷰포트에서도 스크린샷을 떠서 확인할 것.

2026-08-15 발견·수정 (전부 JSON 생성 실수, 뷰어 버그 아님): senmath32_09~12에 solution을 새로 채워 넣는 작업 중 실제 뷰어에 로드해 확인하다가 발견함. 앞선 \n 사례처럼 전부 데이터 생성 스크립트 쪽 실수였고, 이번에도 사용자가 스크린샷으로 지적해서 찾음.

  1. 수식을 닫는 \) 누락: 문제 46개(solution 새로 작성한 것 전부)에서 마지막 수식 블록을 \(로 열기만 하고 \)로 닫는 걸 빠뜨림. renderMathText()는 \(...\)로 정확히 짝이 맞는 구간만 수식으로 바꾸고 나머지는 그대로 escape하므로, 닫는 괄호가 없으면 그 지점부터 문자열 끝까지 전부(백슬래시 명령어 포함) 날것 그대로 노출된다. 매번 open('\(') != close('\)')이면 마지막에 \)를 보충하는 식으로 일괄 수정. solution 문자열을 새로 쓸 때마다 text.count('\\(') == text.count('\\)')를 반드시 스크립트로 검증할 것 — 육안 검수만으로는 긴 문자열 끝의 누락을 놓치기 쉽다.
  2. 지원하지 않는 LaTeX 명령어 사용: 위 "지원하는 LaTeX 명령어" 표에 없는 명령어를 solution에 그대로 써서 백슬래시가 노출됨.
    • \Box(대문자) — 표에 있는 건 \square(소문자)뿐. \Box→\square로 교체.
    • \backsim — 닮음 기호는 \sim만 지원. \backsim→\sim로 교체.
    • \sec, \cot — 목록에 없음. \sec x는 일반 텍스트 sec x로, \cot\theta는 \dfrac{1}{\tan\theta}로 풀어씀.
    • \parallel — 목록에 없음. 유니코드 ∥ 문자를 명령어 없이 직접 텍스트에 넣는 방식으로 대체(어차피 \(...\) 안이든 밖이든 일반 문자는 esc()로 그대로 출력되므로 문제없음).
    새 명령어를 쓰기 전에 반드시 이 문서의 지원 명령어 표와 대조하거나, texToHtml의 parseToken() 소스에서 검색해 실제로 처리되는지 확인할 것.
  3. Python raw string(r'...') 안에 유니코드 이스케이프를 써서 글자가 그대로 노출됨: solution 문자열을 r'...60\u00b0를...'처럼 raw string으로 작성하면 \u00b0가 실제 도(°) 문자로 해석되지 않고 \+u+0+0+b+0 여섯 글자 그대로 남는다(raw string은 이스케이프 시퀀스를 전혀 해석하지 않음). 실제 ° 문자를 직접 타이핑하거나, 유니코드 이스케이프가 필요하면 raw string을 쓰지 말 것.
  4. \n 리터럴 노출 버그 재발: 앞서(2026-08-14) 이미 고쳤던 senmath32_05_q126~137.json의 0132번이 나중에 스키마 전체를 다시 정규화하는 스크립트를 돌리면서 수정 전 원본 업로드 파일을 다시 읽어들이는 바람에 고친 내용이 통째로 사라지고 리터럴 \n이 되살아남. 이미 고친 필드를 다른 이유로 재가공할 때는 항상 "가장 최근에 고친 버전"을 소스로 삼을 것 — 실수로 더 오래된(문제가 있는) 버전을 다시 불러오면 이전 수정이 조용히 사라진다.
